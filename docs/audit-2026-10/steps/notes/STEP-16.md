## 2026-10-25 - `.ifczip` uploads are unpacked before import, with bounded extraction (STEP-16)

- **Type:** Bug
- **Platform:** http://localhost:8000 (backend) — surfaced through the upload dialog and the federated model manager at http://localhost:5173
- **Related tests:** F-012 · `backend/tests/test_step16_ifczip_upload.py`
- **Severity:** P1
- **Observed:** The upload dialog and the federation manager both offer `.ifczip`, and `backend/app/api/projects.py` accepted the extension, but nothing ever unpacked the archive: `import_project_from_bytes` wrote the raw ZIP bytes to `storage/projects/{id}/model.ifc` and `IFCService.validate_ifc` then failed with `Unable to parse IFC SPF header`, surfaced to the user as *"Failed to parse and import IFC file: Error : Unable to parse IFC SPF header"* (a 422 that blamed the user's file for the server's missing extraction step). `POST /api/projects/{id}/models` had the identical defect and additionally left the written archive unlinked after the failure.
- **Expected:** A body whose content starts with `PK\x03\x04` is treated as an archive regardless of the declared extension; the stored `model.ifc` is the uncompressed STEP text that begins `ISO-10303-21;` and opens with `ifcopenshell.open`; `schema_version`/`element_count` describe the extracted model; zero or more than one `.ifc` member is a 422 that names the reason; an oversized or high-ratio member is a 413; a rejected archive leaves no project row and no project directory.
- **Evidence:** Before — `test_step16_ifczip_upload.py`: 5 failed, 1 passed (`assert 422 == 201`, `'no .ifc' not found in 'failed to parse and import ifc file: error : unable to parse ifc spf header'`, `assert 422 == 413`, federation `422 != 201`). After — 6 passed. `backend/tests -q` full run: 49 passed, 1 failed (`test_step01_ai_transform_units.py::test_zero_delta_transform_does_not_move_the_element`, `FOREIGN KEY constraint failed`) — a concurrent lane was running `pytest backend/tests` against the same shared `storage/projects.db` and `storage/projects/` at the time; that test passes in isolation (4 passed), so the failure is cross-process contention, not STEP-16.
- **Suggested fix (applied):** `backend/app/services/project_service.py` gains `IFCZIP_MAGIC`/`MAX_IFCZIP_MEMBERS`/`MAX_IFCZIP_MEMBER_BYTES`/`MAX_IFCZIP_COMPRESSION_RATIO`, `UploadTooLarge(ValueError)` and `extract_ifc_from_ifczip()`, which bounds member count, declared uncompressed size, declared compression ratio **and** the bytes actually read (1 MB chunks, abort at `MAX_IFCZIP_MEMBER_BYTES + 1`, so a forged central directory cannot blow memory), maps `BadZipFile` to `ValueError`, and requires `ISO-10303-21` in the first 512 bytes. `import_project_from_bytes` extracts as its first statement, before `project_id`/`mkdir`, which is what keeps a rejected archive from leaving an orphan directory. `projects.py` runs the STEP magic-header check only for `.ifc` names whose content is not a ZIP, and catches `UploadTooLarge` ahead of the blanket handler to return 413 with a message that names no server path. `federation.py` extracts before `models_dir.mkdir()` and before computing `stored_filename`, stores `{submodel_id}_{stem}.ifc`, and records `file_size = len(step_bytes)`; its `UploadTooLarge` → 413 and `ValueError` → 422 branches run before anything is written, so no unlink is needed for extraction failures (the existing unlink-on-validation-failure block is unchanged).
- **Status:** Ready for review
